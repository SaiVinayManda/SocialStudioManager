## APIs and trust boundaries

Loopback control API: `http://127.0.0.1:8780`. Three independent bearer roles: operator control, n8n orchestration, native worker. No query-string credentials. The health route is nonsecret; other routes authenticate. n8n cannot decide approvals. Workers cannot publish or schedule. Only n8n can call mock publication. There are no arbitrary command, executable, URL or filesystem-root HTTP parameters.

- `POST /intake`: structured job registration; `POST /jobs`: full job submission or `{job_id}` start of a registered job. `GET /jobs/{id}`, `POST /jobs/{id}/cancel`, `GET /jobs/{id}/output`, `GET /jobs/{id}/logs`, `GET /health`.
- Source `{root_id:"generated",relative_path:"horror/pilot-001/final/horror_pilot_001.mp4",expected_checksum:"<sha256>"}`. Registry roots resolve only to project `generated-videos` or `brands/<slug>/inputs`; Windows drives/UNC/links/alternate streams/traversal are rejected. Brand UUID must resolve in the database. An engine job additionally needs a separately preapproved project/digest/expiry in the local worker configuration.
- `POST /jobs/{id}/quality`, `POST /jobs/{id}/approvals`, operator-only `POST /approvals/{id}/decision`. Decision fields: `decision`, exact `checksum`, `content_version`, optional `comments`. `test_mock_only` is valid only for a fixture carrying an acceptance run UUID. Expiry never approves content. GET approval / output metadata / local file download require authentication.
- `POST /scheduler/tick`, `GET /publishing?job_id=<uuid>`, platform-specific mock publish routes, reconcile route; `GET /reports`, local notification history, controlled recovery.
- `POST /ai/tasks`, `GET /ai/tasks/{id}`, `GET /ai/providers/health`: six typed task types, maximum cost zero, mock/failure/fallback only. 9Router/OpenAI/Codex subscriptions are not used as APIs.

Production webhooks: `POST http://127.0.0.1:5678/webhook/social-studio/intake` and `/reports`. Body is a signed `{nonce,timestamp,body,signature}` envelope created with the newly approved local key, never a reusable token in workflow input. API validation consumes each nonce once; 60-second expiry, five-second future skew. Local tokens remain encrypted n8n credentials. Exports contain credential references only. Successful execution data is retained for seven days; failure payload storage is disabled to reduce credential-bearing error capture.

## Folder intake

`services/production-adapter/folder-intake.mjs --config <project-config.json>` polls configured registered brand input folders, requires unchanged size/mtime for five seconds, hashes stable MP4s and submits a signed webhook. No recursive symlink traversal; no shell or downloads. Acknowledgment must contain a durable job ID. SHA/brand idempotency persists in PostgreSQL; in-memory suppression only reduces repeat calls and is not the durability layer. After restart, resubmission returns the same job. New brands are database/registry/config data; no core engine change. Google Drive/OAuth is intentionally not connected.

## Recovery and backup

Only new project services: `docker compose -p socialstudio -f infrastructure/docker-compose.yml stop`. Resume with the same `up -d --pull never`. Never stop unrelated containers. No `down -v`, prune, database reset, key deletion, automatic startup or host-setting change.

Worker leases heartbeat every five seconds and expire after twenty seconds. Recovery retries validation at most three times; interrupted rendering requires manual review to preserve partial outputs. Lost dispatch outcomes enter reconciliation/manual review, not a fresh upload. Expired media verification must run again before dispatch. Content/hash changes invalidate stored approvals through database triggers; the native worker checks actual file bytes immediately before mock dispatch. A file can change outside the database; approval invalidation happens on detection, not via a claimed OS filesystem lock. A future live uploader must upload an immutable verified snapshot; the mock does not establish that guarantee.

Backups: use an owner-controlled `pg_dump` of **only the two new databases**, encrypted and stored outside Git; include n8n encryption-key recovery separately. No backup dump or restored instance is claimed in this checkpoint. Restore must target a new isolated volume and needs its own approval before replacing data. Health/disk retention/restore drills, database restarts and interrupted n8n Wait recovery remain deployed acceptance work.
